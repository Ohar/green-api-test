# Telegram-чат · GREEN-API

Минимальный React-клиент для личных текстовых диалогов в Telegram через
GREEN-API. Адаптация тестового задания для frontend-разработчика: Telegram
выбран из разрешённых ТЗ альтернатив MAX.

- [Приложение на GitHub Pages](https://ohar.github.io/green-api-test/)
- [Релизы](https://github.com/Ohar/green-api-test/releases)
- [Исходный план](IMPLEMENTATION_PLAN.md)
- [Замечания четырёх консультантов](docs/REVIEWS.md)

## Запуск

Нужны Node.js 24.20.x и npm 11+. Версия Node закреплена в `.nvmrc`.

```sh
npm ci
npm run dev
```

Приложение открывается на `http://127.0.0.1:5173/green-api-test/`.
Production-сборка: `npm run build`, просмотр: `npm run preview`.
`base` настроен под путь репозитория GitHub Pages.

## Подключение Telegram

1. Создайте Telegram-инстанс в [кабинете GREEN-API][console] и авторизуйте
   существующий Telegram-аккаунт. QR/код/2FA остаются в кабинете провайдера.
2. Дождитесь состояния `authorized`.
3. Для отдельного тестового инстанса включите уведомления:

   ```json
   {
     "webhookUrl": "",
     "incomingWebhook": "yes",
     "outgoingAPIMessageWebhook": "yes",
     "outgoingMessageWebhook": "yes",
     "outgoingWebhook": "yes",
     "stateWebhook": "yes"
   }
   ```

4. Скопируйте `apiUrl`, `idInstance`, `apiTokenInstance` в форму приложения.
   Поддерживаются `https://<номер>.api.green-api.com` и
   `https://api.green-api.com`. Приложение само настройки не изменяет.
5. Введите международный телефон с кодом страны, нажмите «Создать чат».
   `checkAccount` разрешит телефон в канонический Telegram `chatId`.
6. Отправьте текст. Получатель отвечает из обычного Telegram; ответ
   появляется в том же диалоге.

Если номер скрыт приватностью, проверка телефона может не найти аккаунт.
Тариф Developer на дату исследования поддерживает три чата и 100 проверок
номеров в месяц. Условия следует сверять в [документации тарифов][tariffs].
Не смешивайте разные потребители одной очереди: другую вкладку, браузер,
интеграцию или просмотр чатов в кабинете.

## Возможности и ограничения

- Только личные текстовые диалоги, включая текст со ссылками и emoji.
- Enter отправляет, Shift+Enter переносит строку. Учитывается IME.
- Получение: последовательный HTTP long polling, затем подтверждение
  конкретного уведомления. Дубли и ранние статусы объединяются.
- Принятие сообщения сервисом не выдаётся за доставку или прочтение.
- При неоднозначной сетевой ошибке отправка автоматически не повторяется.
  Проверьте Telegram перед ручным повтором: первое сообщение могло уйти.
- Сообщения, токен и черновики находятся только в памяти вкладки.
  Перезагрузка/отключение очищают их. Удалённые уведомления не являются
  архивом и повторно не восстановятся.
- «Отключиться» не разлогинивает Telegram-инстанс у провайдера.
- Web Locks запрещает двум вкладкам одного origin читать одну очередь.
  Другие браузеры/устройства этим механизмом не координируются.
- Получение работает, пока открыта активная сессия. Фоновая вкладка может
  приостанавливаться браузером. Группы и медиа классифицируются и ACK-аются.
- Токен виден владельцу браузера в его Network: статическая SPA не скрывает
  от него введённый им секрет. Токен автора проекта в сборку не включён.

## Проверки

```sh
npx playwright install chromium
npm run lint
npm run typecheck
npm test
npm run build
npm run test:e2e
```

`npm run verify` выполняет весь набор. Browser-тесты используют production
сборку и проверяют desktop/mobile: вход, создание чата, отправку, получение,
безопасный вывод текста, отключение и второй экземпляр вкладки.
Unit-тесты проверяют контракты API, ACK, дедупликацию, гонки статусов,
потерю авторизации и поздние ответы после отключения.

Тестовая сеть подменяется обезличенными fixtures; реальные сообщения
автотесты не отправляют. Учётные данные GREEN-API при разработке не
предоставлялись: **живая доставка и CORS с реальным инстансом ещё не
подтверждены**. Проверка OPTIONS без реального токена завершилась сетевым
таймаутом и не доказывает ни поддержку, ни отсутствие CORS.

Для завершения живой приёмки выполните шаги подключения на опубликованном
адресе с двумя своими Telegram-аккаунтами. При CORS-ошибке сначала проверьте
точный `apiUrl` и доступ из вашей сети. GitHub Pages не выполняет серверный
код; если провайдер запрещает прямые запросы, потребуется отдельный
ограниченный транспортный сервер, описанный в исходном плане. Публичные
CORS-прокси для токенов использовать нельзя.

## Правила исходников

ESLint использует recommended-конфигурации React, React Hooks,
TypeScript и jsx-a11y, проверку React Refresh и ESLint Stylistic:

- без точек с запятой;
- пустая строка вокруг блоков и перед `return`;
- максимум 80 символов в строке исходного JS/TS/TSX;
- максимум 1000 строк в исходном файле, включая пустые строки и комментарии.

ESLint 9 выбран по совместимости peer dependencies React/a11y плагинов;
версии зависимостей зафиксированы lockfile.

Компонент оформляется папкой с публичным `index.ts`, например:

```text
ChatPanel/
  index.ts                  # экспорт компонента и публичных props
  ChatPanel.tsx
  ChatPanel.module.css
  constants/
  helpers/
  hooks/
```

Модульные константы и служебные функции выносятся рядом с компонентом.
Локальные переменные и обработчики его событий могут оставаться внутри.
`npm run check:architecture` проверяет эту структуру, публичные экспорты
и запрещает импорт приватных файлов другого компонента.
Доменная логика отдельно в `src/core`, транспорт — в `src/api`.

## GitHub Pages и релизы

Публикация запускается при push тега `vX.Y.Z`, созданного `npm version`.
Обычный push исходников запускает CI без публикации.

Однократные настройки GitHub:

1. Settings → Pages → Source: **GitHub Actions**.
2. Environment `github-pages` должен разрешать теги релизов `v*`.
3. Actions должны иметь права, заявленные workflow: build — чтение,
   deploy — Pages/OIDC, release — запись contents. Секреты GREEN-API
   не нужны ни в Actions, ни в переменных сборки.

Выпуск после установки зависимостей и браузера:

```sh
git switch master
git pull --ff-only
# внесите и закоммитьте изменения
npm version patch
```

Для несовместимого изменения используйте `major`, для новой функции `minor`.
До выпуска рабочее дерево должно быть чистым. Lifecycle `preversion`
проверяет ветку, origin и запускает проверки. Npm создаёт commit и tag.
Lifecycle `postversion` атомарно отправляет только текущую ветку и новый тег;
не публикует все локальные теги.

Настоящий Git hook `.githooks/pre-push` проверяет соответствие версии тега
и `package.json` в tagged commit. Он устанавливается через npm `prepare`.
Git не имеет стандартного `post-tag` hook: публикация на сервере реализована
событием tag push в GitHub Actions. CI повторяет проверки даже при обходе
локального hook. Workflow проверяет принадлежность релиза `master`,
тестирует production-сборку, публикует Pages, затем создаёт GitHub Release
с архивом `green-api-test.tar.gz`.

Если проверки `preversion` упали, версия ещё не изменена. Если push после
создания тега не удался, устраните проблему доступа и отправьте уже созданные
ветку и тег атомарно — не вызывайте `npm version` второй раз автоматически.
Если Actions упал, откройте лог и повторите упавшую job после устранения
внешней причины; для изменения исходников выпускайте следующий патч.

## Безопасность публикации

Production CSP допускает только локальные скрипты/стили и запросы к
разрешённым GREEN-API-хостам. В сборке нет `unsafe-inline` и localhost.
Все API-запросы запрещают redirect, cookies и кеширование.
Ошибки не содержат сырые URL или ответы с токеном.

GitHub Pages не позволяет проекту задавать произвольные HTTP security
headers. CSP и referrer policy заданы через meta; `frame-ancestors` через
meta не работает, поэтому защита этим заголовком здесь не заявляется.
Не добавляйте production-токены в `.env`, `VITE_*`, fixtures, отчёты или Git.
